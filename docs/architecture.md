# Lanwell architecture

Lanwell is a desktop app for mounting other machines' shares (SMB, as
folders here) and for sharing folders on the network (Samba and NFS). This document records how
the pieces fit and why. Change the decisions at the end deliberately, and
update this file when you do.

## Goals

- **Plain-language network sharing**: no smb.conf, /etc/exports or fstab
  knowledge needed.
- **Never break a hand-configured system.** Lanwell writes files of its own and
  leaves everyone else's alone (one `include` line in smb.conf is the only
  exception).
- **Honest about the protocols.** Samba has users and passwords; NFS trusts
  machines. The UI says so instead of pretending they're the same.
- **Linux first.** macOS later if it's wanted: the same core and UI, with a
  different helper per OS.

## Components

```
crates/
  core     lanwell-core: the model (shares, exports), validated names, the requests the
           helper accepts, the state file, and rendering the config files. No I/O beyond
           reading files; no root; no D-Bus. Everything here is unit-tested.
  helper   lanwell-helper: the only part that runs as root. A system D-Bus service that
           checks each request with polkit, then applies it: writes config, reloads services.
           `lanwell-helper install` puts it in place (the app's Install button runs it).
    linux/   The D-Bus, systemd and polkit files that install it.
  app      The desktop app (Tauri 2). Thin commands over core; changes go to the helper.
    ui/      Solid + TypeScript + Tailwind v4. Talks to the backend only through api.ts.
scripts/
  install-helper-dev.sh   Installs a debug helper so the app can make changes in development.
```

Rules that keep this layering useful:

- **Logic lives in `core`**, not in Tauri commands or D-Bus handlers. Those
  parse input, call core, and shape output.
- **`ui/src/api.ts` is the only way the UI reaches the backend.** Types for
  everything it sends and receives come from the Rust structs (ts-rs,
  regenerated by `cargo test` into `ui/src/bindings`; commit them).
- **The helper accepts outcomes, not edits.** A request says "these are the
  shares", never "write this file". Nothing the app sends can name a file the
  helper will write.
- **Every value that reaches a config file is a validated type** (`names.rs`).
  Validation runs on deserialization too, so the helper re-checks whatever the
  app sends.

## How a change is made

```
UI (api.ts) ──invoke──▶ app (commands.rs) ──D-Bus: Apply(json)──▶ helper (bus.rs)
                                                                    │
                                     polkit: may this caller do it? ◀┘ (password prompt)
                                                                    │
                     apply.rs: update state.json, regenerate config ┘
                               files from it, reload the service
```

- The helper is started by D-Bus on first use and exits after two idle minutes.
- Each kind of request has its own polkit action
  (`io.github.obscuredetour.lanwell.manage-shares`,
  `io.github.obscuredetour.lanwell.set-password`), so an administrator can
  allow one without the other.
- Requests are applied one at a time.

## Installing the helper

A package installs the helper and its D-Bus, systemd and polkit files. A
Lanwell that didn't come from one installs them itself: when
`lanwell-helper --version` (run as the user) is missing or names another
version, the app offers an Install (or Update) button, which runs
`pkexec lanwell-helper install` with the helper that sits beside the app's own
binary. pkexec shows the desktop's password prompt; the helper then copies
itself to `/usr/lib/lanwell` and writes the files, which are built into it.

pkexec runs that binary as root, so it must come from the same place as the
app: anyone who could replace it could replace the app too. Once installed,
the helper D-Bus runs is the root-owned copy.

**Before release builds:** offer the button only when the helper beside the
app, and the folders above it, are owned by root and writable by no one else
(as in a deb or rpm). Otherwise anything running as the person could replace
it, and the app's "different build" check would ask them to install it.
Development builds (`target/debug`) are exempt.

## Running the servers

Saving shares or exports starts the server they need, and has it start with
the computer (`systemctl enable --now`), if it's installed: Samba is `smb` on
Arch and Fedora and `smbd` on Debian and Ubuntu; the NFS server is
`nfs-server`. Removing every share leaves it running, since shares set up by
hand may need it; the Samba and NFS pages show its state with Start and Stop.

Opening the firewall is the person's choice, not a side effect: those pages
say when the firewall blocks the server, and offer **Allow from local
network**. With ufw that's one rule per private address range (10.x,
172.16–31.x, 192.168.x, and IPv6's local ranges if ufw handles IPv6), only
for the server's port (445 for SMB, 2049 for NFS 4), commented `lanwell`.
With firewalld it's the `samba` or `nfs` service in the default zone, whose
trust level decides who's let in. Lanwell records what it opened, and
**Stop allowing** only takes that back. The status is read without root:
ufw's saved rules where they're readable, `firewall-cmd --query-service`.

## Sharing safely

Shares and exports of system folders (`/`, /etc, ...) are refused, checked
again on the real path once symbolic links are followed. Drives in
/run/media (`/run/media/main`, `/run/media/alice/backup`) aren't system
folders: many distributions and desktops mount drives there.

An NFS export on a drive other than the system's own gets `mp=<that drive's
mount point>`, so it's only exported while the drive is mounted; otherwise
NFS would serve the empty folder underneath. The drive is found in the
kernel's mount table, not by device numbers, which btrfs subvolumes would
fool. An export in /run/media whose drive isn't mounted is refused. Samba passwords can
only be set for people's accounts (UID 1000 and up), not root or system ones.
The app warns before exporting read-write over NFS to every machine (`*`),
since NFS trusts what each client says about who its users are.

## Files Lanwell owns (Linux)

| File | What it is |
|---|---|
| `/etc/lanwell/state.json` | The source of truth: every share and export Lanwell manages. World-readable, no secrets, so the app reads it without a password. |
| `/etc/samba/lanwell.conf` | Generated share sections. Included from smb.conf. |
| `/etc/exports.d/lanwell.exports` | Generated exports. `exportfs` reads every file in exports.d. |
| `/etc/samba/smb.conf` | Not Lanwell's. It gets one `include` line; if there's no smb.conf at all (Arch ships none), Lanwell writes a minimal one, which is the user's from then on. |
| `/etc/systemd/system/<mount point>.mount` | A mount, as a systemd unit named after its folder (`systemd-escape --path`). |
| `/etc/systemd/system/<mount point>.automount` | For a mount that waits to be opened: mounts it on first access. |
| `/etc/lanwell/credentials/<mount point>` | A mount's user name and password, for mount.cifs. Mode 600, in a 700 folder: only root can read them. Never in the state file. |

Generated files are never parsed back: they're rewritten from the state file
on every change, and say so at the top.

## Mounting other machines' shares

A mount is an SMB share (`//nas.lan/media`) or an NFS export
(`nas.lan:/srv/media`), as a systemd `.mount` unit (`Type=cifs` or
`Type=nfs`), like an fstab line with `x-systemd.automount`, without touching
fstab. The protocols differ in two ways that show in the UI: SMB signs in
(a user name and password, or as a guest), while NFS has no sign-in (the
server's export list decides which machines may mount); and an SMB mount's
files appear as the person who added it, while an NFS mount's keep the
server's user IDs. When it connects is the
person's choice:

- **When first opened** (the default): an `.automount` unit is enabled, and
  the share mounts when something opens the folder. Startup never waits for
  the server. Lanwell also mounts it once straight away, so a wrong password
  shows up while the person is still in Lanwell.
- **At startup**: the `.mount` unit is enabled itself (`WantedBy=remote-fs.target`).
  Startup waits for the server, up to `TimeoutSec=30`, every time it's off;
  the UI says so before it's chosen.

An SMB mount's files appear as the person who added it, readable only by
them (`uid`/`gid` with `forceuid`/`forcegid`, modes 0600/0700); the helper
takes the account from D-Bus, not from the request. Mounts are `nosuid,nodev`: the
server decides what's on a share, so nothing on it may run as another user.
Mounts default to `~/Network/<share>`; the app creates a folder in the
person's home itself, so it's theirs.

The helper refuses system folders (/etc, /usr, ...), folders whose path has
a symbolic link in it, and folders with files in them. It only replaces or
removes mounts it recorded in its state: a folder with any other mount (an
admin's unit, an fstab line, anything mounted now) is left alone.

When mounting fails, the helper reads what mount.cifs or mount.nfs logged
for that attempt and explains it ("The server didn't accept the user name or
password" for `mount error(13)`). The mount stays saved, so it can be fixed
and tried again. The app shows each mount's state (connected, connects when
opened, couldn't connect) by asking systemd, without root, and can list a
server's SMB shares with `smbclient` (its password passed in `$PASSWD`, not
on the command line) and its NFS exports with `showmount` (which only NFS 3
servers answer; for NFS 4-only ones, the path is typed).

**Finding servers.** The app (not the helper: looking needs no root) listens
for mDNS (Bonjour) announcements of `_smb._tcp` and `_nfs._tcp` for a few
seconds, with the `mdns-sd` crate, so it doesn't depend on Avahi. Macs, NAS
boxes, and Linux machines with Avahi announce SMB; Windows PCs don't (they
use WS-Discovery), and few servers announce NFS, so their addresses are
typed.

**Editing.** An edit is a `SetMount` for the new settings, with `replaces`
set to the mount's old folder. If the folder changed, the helper checks the
new one first, then moves the saved password across and removes the old
mount; an empty password field keeps the saved one. An SMB address can name
a folder inside a share (`//nas.lan/media/films`); NFS addresses always
could.

## macOS (later, if wanted)

The core and UI carry over; the helper and the config rendering don't.

- **SMB sharing** is built into macOS (Apple's own server, not Samba). Shares
  are managed with the `sharing` command; users are ordinary macOS accounts
  (or "Sharing Only" ones).
- **NFS exports**: macOS still ships `nfsd`. Exports go in `/etc/exports`
  (BSD syntax, unlike Linux's) and `nfsd enable` starts it. NFSv3 only.
  Exporting privacy-protected folders needs Full Disk Access for `/sbin/nfsd`.
- **The helper** would be a launchd daemon registered with `SMAppService` and
  reached over XPC, which needs a signed, notarized app. The requests stay
  the same `lanwell_core::Request`; only the transport changes.
- **Mounting** needs no helper at all: the NetFS framework mounts as the user,
  with credentials in the Keychain.

## Roadmap

1. **Share-only users**: a user name and password for a share, separate from
   anyone's login, and unable to log in. Files they write are owned by the
   folder's owner (`force user`), so permissions stay as they were.
2. **Packaging**: AUR first, then deb and rpm, each installing the helper
   itself. A release bundle needs the helper beside the app (a Tauri
   sidecar) for the Install button; today only `cargo tauri dev` builds it
   there, and the root-ownership check above has to come first
   ([issue #1](https://github.com/obscuredetour/lanwell/issues/1)). Flatpak's
   sandbox can't run pkexec on the host, so it doesn't fit.
3. **Finding Windows PCs** (WS-Discovery), which don't announce over mDNS.
   Not urgent: no one working on Lanwell has a Windows PC to test with. When
   it's requested or built, it will need someone with one to help test (a
   PC sharing a folder on the same network as Lanwell).

4. **macOS, later, if people want it.** macOS already shares and mounts SMB
   from its own settings, so Lanwell would add little there for a lot of work:
   a signed, notarized helper (see "macOS (later, if wanted)" above). Its
   real gap is NFS exports, which have no GUI. The shared core and per-OS
   helpers keep the door open.

## Decisions

- **2026-10-11: JSON over D-Bus.** The helper's one method takes a JSON
  `Request`. The app and helper share the Rust types, so they can't drift, and
  validation happens as it's decoded. D-Bus-native types would duplicate the
  model for no gain while both ends are ours.
- **2026-10-11: A state file, not parsing config.** Parsing smb.conf and
  exports back is fragile and would tempt Lanwell to edit what it didn't write.
- **2026-10-11: polkit via D-Bus, not pkexec.** pkexec runs a whole program as
  root with arguments the caller chose; a D-Bus service accepts only its typed
  requests and identifies the caller race-free.
- **2026-10-11: The helper installs itself, with pkexec.** So a Lanwell that
  didn't come from a package (a development build, a downloaded bundle) can
  be set up with one button and the system's password prompt. One install
  path, `lanwell-helper install`, serves the button and the dev script.
- **2026-10-11: Opening the firewall asks.** Starting a server when
  something's shared is what sharing means; letting it through the firewall
  is a separate choice (a laptop's firewall also guards it on others'
  networks), so it's a button, and then only to the local network.
- **2026-10-11: One mount type for both protocols.** A mount is a folder
  plus a remote share, SMB or NFS, so ownership checks, units, status and
  hardening are written once. State files from before (`smbMounts`) are
  converted when they're read.
- **2026-10-11: Sharing before mounting** for the first slice, because it
  exercises every part of the helper with the fewest moving parts.
